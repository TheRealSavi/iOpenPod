# PhotosDB binary format notes

## Scope and evidence

These notes translate Photo Database knowledge from the Original iOpenPod into the
iOpenPod 2.0 format layer. The primary local evidence is:

- `src/iopenpod/sync/photos.py` for Photo Database parsing, record creation, album
  membership, file-format records, and path strings;
- `tests/test_photo_encoding.py`, `tests/test_photo_path_safety.py`, and
  `tests/test_photo_browser.py` for exercised behavior; and
- the existing ArtworkDB implementation and
  [`artworkdb-format.md`](artworkdb-format.md) for the common binary layouts.

The Original iOpenPod is evidence rather than a runtime dependency. The golden
fixture under `tests/fixtures/PhotosDB/` was generated by its photo writer and is
retained as a fixed compatibility vector.

## Artifact and format relationship

The device artifact is normally stored at `Photos/Photo Database`. iPodDB calls its
typed parser/writer API PhotosDB to distinguish that artifact from ArtworkDB and
from the source-neutral `PhotoLibrary` projection.

PhotosDB uses the same observed Chunk grammar as ArtworkDB:

```text
mhfd
├── mhsd type 1
│   └── mhli
│       └── mhii ...
│           ├── mhod type 5
│           │   └── mhni
│           │       └── mhod type 3 (full-resolution path)
│           └── mhod type 2 ...
│               └── mhni
│                   └── mhod type 3 (thumbnail path)
├── mhsd type 2
│   └── mhla
│       └── mhba ...
│           ├── mhod type 1 (album name)
│           └── mhia ... (image membership)
└── mhsd type 3
    └── mhlf
        └── mhif ...
            └── optional mhod type 3 (file path)
```

The nested Header and MHOD payload representations are shared with ArtworkDB so
known field offsets and encodings have one implementation. PhotosDB has its own
nominal `MhfdHeader`, Database Definition, Chunk-definition graph, contextual parser
registry, builder, and public parser/writer seams. Passing an ArtworkDB document to
the PhotosDB writer, or the reverse, fails rather than relying on their equal root
marker.

## Photo-specific meanings

The Photo Database uses MHII offset `0x28` as the original/creation timestamp,
offset `0x2C` as the EXIF taken/digitized timestamp, and offset `0x30` as the source
image size. Original iOpenPod emits unsigned Unix seconds for the timestamps.

Each photo normally has one type-5 MHOD whose MHNI names the full-resolution image,
followed by one or more type-2 MHODs whose MHNI records identify thumbnail formats,
byte offsets, sizes, visible dimensions, and padding. The type-3 path string uses
UTF-16 little-endian and the colon-separated device spelling observed in iPod
databases, such as `:Thumbs:F1017_1.ithmb`.

For PhotosDB thumbnails, Original iOpenPod's writer centers the fitted image on a
black raster and records one side's horizontal and vertical margin as MHNI padding.
The MHNI width and height each include the leading margin; the stored raster also
contains the matching trailing margin. A reader therefore decodes a stored size of
`(width + horizontal padding, height + vertical padding)`, then crops from the
padding origin to a visible size of
`(width - horizontal padding, height - vertical padding)`. This PhotosDB meaning is
distinct from ArtworkDB's ordinary row-stride or trailing-padding behavior.

MHBA `album_type` 1 denotes the master Photo Library. Original iOpenPod uses 2 for
ordinary albums on most devices and 6 for the observed Nano 6 and Nano 7 policy.
The format layer preserves or accepts that value; it does not choose a Device
Profile. MHIA children preserve ordered image membership. Slideshow flags and
durations remain typed MHBA Header fields.

For an empty user-album addition over a retained PhotosDB, iOpenPod 2 allocates the
next identity above all retained Photo and Photo Album identities, appends the MHBA
after retained albums, and writes one type-1 album-name MHOD. Device Registry, not
the format layer, selects ordinary album type 2 or the Nano 6/7 type 6 policy.

MHIF records associate a format ID with one fixed image size. An MHIF may contain a
type-3 path child, although Original iOpenPod's current photo writer omits it and
derives `F<format>_1.ithmb`.

## Root values and construction

Original iOpenPod writes 6 at MHFD offset `0x10` for newly created Photo Databases
and begins photo and album identities at 100. These are creation policies, not a
universal interpretation of the field. `new_PhotosDB` therefore requires the root
value and next MHII identity explicitly rather than inspecting a device or guessing
from a format ID.

The builder creates the standard image, album, and file-format datasets through the
same registered definitions used by the parser and writer. Derived Chunk lengths
and child counts belong to the shared writer.

## Lossless writing and boundaries

Parsed Headers, bodies, payload encodings, padding, Unknown Chunks, and bytes beyond
the declared root extent are retained. An unchanged parse/write round trip must be
byte exact. Structured edits patch only their known representation while the writer
repairs affected extents and counts and validates child ordering and contextual MHOD
payload shapes.

The PhotosDB artifact API accepts bytes and returns a root-typed Database Document
or serialized bytes. It does not accept a Mount Point, open
`Photos/Photo Database`, select a Device Profile, read or write
iTHMB/full-resolution files, or publish device changes. `iPodDB.library` separately
projects and reconciles supported semantic Photo edits over the retained document;
the Application Layer and Storage retain capability, I/O, and publication authority.
